Two-way binding between the application and a single signal on a named object in the user interface. received fires when the UI emits the signal — a button click being the everyday case — and triggering emit raises the same signal on the UI object from the application side.

This is the event counterpart to the UI Bool / Int / Real / String blocks, which carry values. UI Event carries no data at all: it is a pure notification in either direction. Where a click needs to be accompanied by a value, pair this block with the matching UI data block on the same object.

The target is named by the two parameters: Object selects the UI object and Signal selects the signal on it. The default Object _qml_root_object_ is a sentinel meaning “the first root object of the UI”, so a single-window UI needs no naming at all. For anything else, set Object to the name the object is declared with in the UI definition (objectName in QML).

Only parameterless signals are supported. The name is used exactly as written, with no Changed suffix and no camel-casing. A signal declared signal accepted() in QML, or any C++ signal of the same shape, binds directly. For receiving, a single-boolean form such as clicked(bool) also binds as a fallback, but the argument is discarded — only the fact that the signal fired reaches the application. Any other signature will not bind. Emitting always uses the parameterless form, so a signal that requires arguments cannot be raised from emit.

Binding is deferred. The UI often loads after the application starts, so the object lookup is retried in the background until the object appears. An emit issued before the UI has loaded raises no signal.

Watch for feedback loops. Emitting a signal is indistinguishable, from the UI's point of view, from the UI emitting it itself — so an emit on a bound signal comes straight back as received on this same block. Wiring received back to emit gives an unbounded loop with nothing to break it.

The block is only built for targets whose HAL implements the UI binding layer (currently the Qt/QML targets).

In Ev.
emit Raise Signal on Object, as though the UI had emitted it, then fire done. Anything the UI has connected to that signal runs, and this block's own received fires too.
Out Ev.
done Fires once the emit request has been handed to the UI layer. It does not indicate that the signal was accepted — if the object has not loaded yet, or the signal name does not resolve, nothing is raised and done still fires.
received Fires when the bound signal is emitted in the UI, for example when the user clicks the bound button. Asynchronous: it is not a response to any input event on this block.
