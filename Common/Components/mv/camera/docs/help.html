Camera opens a video capture device or file and provides frames for downstream machine vision processing. It supports V4L2 cameras (via OpenCV or libcamera), USB cameras, and video files. Frames are referenced by a stream ID and consumed by Frame Resize, Frame Crop, Frame Format, Frame Show, and ML inference blocks.

Resolution and frame rate parameters are hints. Set them to 0 to accept whatever the device provides. The actual dimensions of each captured frame are reported on the width and height output ports of grabFrame.

The camera_id parameter (and the optional device_id input port) selects the capture source. Two formats are accepted:

Format Example Behaviour
Non-negative integer 0, 1, 2 Opens camera /dev/videoN. The block tries the standard OpenCV/V4L2 backend first. If that fails and the build includes libcamera support and the system has the required DMA-buf heap devices, it automatically retries using libcamera — allowing MIPI/CSI cameras (e.g. Raspberry Pi Camera Module) to work without any configuration change. The block fires err with error code 5 (not found) if /dev/videoN is absent.
File or device path /dev/video0, /tmp/test.mp4 Opens the path directly using the standard OpenCV/V4L2 backend only. No libcamera fallback is attempted. Useful for specifying a device by its stable path (e.g. /dev/v4l/by-id/…), a named pipe, or a video file. Use an integer index if libcamera fallback is needed. The block fires err with error code 5 (not found) if the path does not exist.

Finding the correct camera index on Linux. Use v4l2-ctl --list-devices to list all V4L2 devices and their /dev/videoN nodes. Then verify the supported formats and frame sizes with: 

v4l2-ctl -d /dev/video0 --list-formats-ext

Note that a single physical camera often creates several /dev/videoN nodes (e.g. video0 for raw capture, video1 for metadata). Try the lowest-numbered node that reports a supported pixel format. If OpenCV cannot open the device but v4l2-ctl can, check that no other process holds the device open and that the user has read/write permission on the node.

libcamera mode (Raspberry Pi and compatible boards). When the build is compiled with EHS_USE_LIBCAMERA, the block attempts to use libcamera instead of the standard OpenCV V4L2 backend. libcamera requires kernel DMA-buf heap devices (/dev/dma_heap/linux,cma or /dev/dma_heap/reserved, and /dev/udmabuf). If those devices are absent the block fires err with error code 3 (open error) rather than crashing. Use an integer device index with libcamera mode; path-based IDs are not supported.

Resolution and FPS negotiation. OpenCV passes the requested width, height, and fps to the driver as hints via CAP_PROP_FRAME_WIDTH / CAP_PROP_FRAME_HEIGHT / CAP_PROP_FPS. The driver silently rounds to the nearest supported mode — it does not fail if the exact values are unavailable. Setting any of these to 0 skips the hint and uses the driver default. After grabFrame fires the actual dimensions are available on the width and height output ports.

Name Type Default Description
camera_id S Camera device index or path. Integer 0 opens /dev/video0, 1 opens /dev/video1, etc. A non-integer string is treated as a file or device path. Leave blank to use the value supplied on the device_id input port at runtime.
fps I 0 Requested capture frame rate in frames per second. 0 = don't care (use device default). The driver selects the nearest supported rate; the parameter does not fail if the exact value is unavailable.
width I 0 Requested capture width in pixels. 0 = don't care (use device default). The driver rounds to the nearest supported width. The actual captured width is reported on the width output port after grabFrame.
height I 0 Requested capture height in pixels. 0 = don't care (use device default). The driver rounds to the nearest supported height. The actual captured height is reported on the height output port after grabFrame.
asynchronous B 0 When 1, a background capture thread continuously grabs frames so that grabFrame returns immediately with the most recent frame. When 0, grabFrame blocks until the camera delivers the next frame. Async mode is recommended when grabbing frames from the main EHS thread to avoid stalling other function blocks.
show_frame B 0 When 1, each captured frame is displayed in a debug preview window with an FPS overlay. Only supported in desktop builds with a display (requires OpenCV highgui). This is a debug option only; only one camera instance can use it at a time.
greyscale B 0 When 1, captured frames are delivered as 1-channel greyscale. Support depends on the backend: libcamera-based devices (Raspberry Pi CSI cameras) generally support this natively. V4L2/USB cameras may not; if the driver ignores the hint the frame will still be BGR and downstream processing will need to convert it.
OpenCL Acceleration I 0 0 = CPU (cv::Mat, default). 1 = OpenCL GPU (cv::UMat). When enabled, Frame Resize, Frame Crop, and Frame Format operations run on the OpenCL GPU and frame data stays on the GPU between operations. Call EhsCameraFrameEnsureCPU (or connect the frame to a CPU-only block such as a TFLite inference block) to download the frame to CPU memory before ML inference. Not supported on Raspberry Pi VideoCore GPU.

grabFrame
In Ev.Type
capture Captures the next frame from the camera. In synchronous mode this blocks until the camera delivers a frame. In asynchronous mode it returns the most recently buffered frame immediately. Fires -- only if a frame was successfully captured; fires nothing on failure (connect a watchdog timer if frame delivery must be guaranteed).
Data InType
show B When true, displays the captured frame in a debug preview window. Overrides the show_frame parameter at runtime. Only functional in desktop builds with a display.
Out Ev.Type
-- Fired when a frame was captured successfully.
Data OutType

width I Actual width in pixels of the captured frame. May differ from the requested width parameter if the device rounded to a supported resolution.
height I Actual height in pixels of the captured frame. May differ from the requested height parameter if the device rounded to a supported resolution.

In Ev.Type

Error Codes Top ↑ Misc ↓ Ports ↑ Params ↑

The errno output port on startCamera carries one of the following values. Connect it to a data display or integer comparison block to surface the failure reason at runtime.

Value Name Meaning Common causes & remedies
0 OK Camera opened successfully. —
1 FAILED Generic failure. Unexpected error not covered by more specific codes. Check the runtime log for details.
2 IN_USE Camera already open. startCamera was fired while the camera was already running. Fire stopCamera first, or guard the start event so it only fires once.
3 OPEN_ERR Device exists but could not be opened.
  • Another process holds the device open exclusively (e.g. a previous crash left the device locked — restart may be needed).
  • Insufficient permissions: check ls -l /dev/video0 and that the user is in the video group.
  • The device reported an unsupported format or pixel mode.
  • libcamera mode: OpenCamera() threw an exception (e.g. no compatible sensor pipeline, or DMA-buf heap devices absent). Check /dev/dma_heap/ and /dev/udmabuf exist.
4 MEM_ERR Memory allocation failure. Insufficient permanent heap. Check EHS heap configuration. This error is very uncommon on normal hardware.
5 NOT_FOUND Device node or file path does not exist.
  • The camera_id integer index has no corresponding /dev/videoN node. Use v4l2-ctl --list-devices to find the correct index.
  • A path-format ID points to a file or device that does not exist.
  • The camera is not plugged in or the kernel driver has not loaded (lsmod | grep uvcvideo).
  • On Raspberry Pi, multiple /dev/videoN nodes exist for one camera; try incrementing the index until a working one is found.

Diagnosing “never finds the camera” problems. If startCamera consistently fires err even when v4l2-ctl reports the device with matching parameters:

  1. Connect the errno output to a display to confirm the error code.
  2. Error 5: the index or path is wrong — verify with v4l2-ctl --list-devices.
  3. Error 3: the device exists but OpenCV cannot open it. Try ffplay /dev/video0 or python3 -c "import cv2; c=cv2.VideoCapture(0); print(c.isOpened())" to test independently of inxware.
  4. Error 3 after a crash: the previous session may have left the device locked. Restarting the application (or the system) usually resolves this.
  5. If v4l2-ctl --list-formats-ext -d /dev/video0 shows multiple resolutions, try setting width and height to 0 to let OpenCV choose rather than requesting a specific size that may be mismatched.
